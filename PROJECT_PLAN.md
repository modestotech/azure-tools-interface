# PROJECT_PLAN — APIM ↔ Entra access mapper

> Nothing gets committed until you OK it (per CLAUDE.md › Git).

## Context

`CLAUDE.md` is the spec for a static, backend-less React SPA. You paste an ARM token and a Graph token, and the app maps every APIM operation to:
- the policies that protect it,
- the Entra principals that can call it, and
- the backend it routes to, including how APIM authenticates outbound.

While data loads, a developer-facing "Matrix-style" request log streams the live ARM/Graph traffic. I have no Azure access, so I build everything against fixtures and MSW.

## 1. Target setup (scope)

The goal is **one company's APIM pattern**, not every possible APIM setup. The reference is `samples-raw/api-policy.xml`, an **API-scope** policy that each API carries.

**Analysis scope: exactly one API.** The user picks subscription → APIM instance → API, and there is no "all APIs" option. Instance-wide calls are limited to filling the pickers (subscriptions, services, API names), the service itself (`identity`) and the global policy.

| Section | Content | What the app does with it |
|---|---|---|
| `inbound` | **No `<base/>`**, so global and product inbound policies are *not* inherited | Show "parent inbound ignored" on the API |
| `inbound` | `validate-jwt`: `openid-config` (v2), one `audience`, v1 + v2 `issuers`, `required-claims` `roles` `match="any"` | Inbound access rule |
| `inbound` | `set-backend-service backend-id="…"` | Link to the backend entity |
| `inbound` | `authentication-managed-identity resource="…" client-id="…"` | Outbound auth through a **user-assigned** identity |
| `backend` / `outbound` / `on-error` | `<base/>`, header cleanup, `Request-Id` echo, JSON error body (with `@(...)` expressions) | Not access-related: ignored, not flagged |

**How the joins work in this pattern**

- **Inbound (who can call):**
  1. Find the API's service principal from `audience`. A GUID is looked up as an `appId`; `api://…` or another URI is looked up with the `servicePrincipalNames` filter.
  2. Required `roles` values → `appRoles` on that service principal.
  3. `appRoleAssignedTo` → users, service principals and groups, then each group's direct members.
  4. `match="any"`: holding **one** listed role is enough.
- **Outbound (what APIM calls with):**
  1. `client-id` → the user-assigned identity in the APIM service's `identity.userAssignedIdentities` whose `clientId` matches → its `principalId`.
  2. `resource` → the target service principal, via the `servicePrincipalNames` filter.
  3. That identity's `appRoleAssignments`, filtered to the target service principal → the app roles APIM holds on the backend.
- **Backend:** `backend-id` → the backend entity and its `url`. Backends are identified by URL only: the Azure resource behind one (e.g. a Container App) is not looked up, so there's no `GET {resourceId}`.

**Out of scope for now:** `validate-azure-ad-token`, `check-header`, `include-fragment`, named-value resolution, `choose`, `send-request`, `set-backend-service base-url`, Pool backends and product-scope policies. The parser doesn't support them. Any of them found in `inbound` or `backend` becomes an `UnresolvedRule` ("needs manual review") so the app never stays silent. Elements that only affect responses (`set-header` other than `Authorization`, `rate-limit*`, `quota*`, `cors`, plus everything in `outbound` and `on-error`) are ignored.

**Assumptions (correct me if wrong):**
1. The `__X__` placeholders are filled in at deploy time, so the live policies contain literal values (no `{{named values}}`).
2. Operations usually have no policy of their own. If one does, it is composed generically: `<base/>` pulls in the API policy.
3. A global policy may exist. It's fetched (one call), but its `inbound` only applies to an API whose inbound includes `<base/>`.
4. Backends are `Single`.

**M1 — `lib/` foundations**
- `lib/token`: JWT decode (`aud`, `tid`, `upn`/`oid`, `exp`) plus checks for audience, tenant and expiry. Unit-tested.
- `lib/http`: an HTTP client (`createHttpClient()` in `lib/http/client.ts`) with:
  - the auth header, and an `aud` guard before each request batch
  - GET-only enforcement; the only exception is POST to `https://graph.microsoft.com/v1.0/$batch`, and only when every sub-request is a GET
  - paging (`nextLink` / `@odata.nextLink`)
  - 429 `Retry-After` handling
  - a concurrency limiter (8 in flight)
  - typed errors (`Unauthorized` carries the az command to copy, plus `Forbidden` and `NotFound`)
  - token redaction in every error message
- `lib/http/requestLog`: an in-memory event bus (Zustand slice, ring buffer of about 2,000 entries).
  - Each entry: id, method, masked URL, status, duration, bytes, retry count, query key, and pending/ok/error state.
  - The wrapper emits on start and on finish, so the log covers every call with no per-call wiring.
- `app/session` store: tokens, sub ID and tenant ID, held in memory only. A unit test asserts nothing reaches `localStorage` or `sessionStorage`.
- **Security hardening (done, from the security review):**
  - `encodePathSegment()` in `lib/http/odata.ts` rejects `.`, `..`, `/`, `\`, `?`, `#` and control characters with `invalid-request` and percent-encodes the rest.
  - `readOnly.ts`: a `$batch` sub-request URL must be a plain relative path, with no `.`/`..` segment, `//`, `\` or percent-encoded dot or slash.
  - `fetchOnce` sends with `redirect: 'error'` and `credentials: 'omit'`.
  - `lib/token/ids.ts`: `setSubscriptionId` stores only a GUID, `setTenantId` only a GUID or domain name (otherwise `''`, returning `false`). `azTokenCommand` falls back to `<TENANT_ID>` on an invalid value.
  - The log export carries `errorKind` instead of the error text.
  - Demo mode fails unmocked ARM/Graph calls instead of passing them to real Azure.
- **Architecture review follow-ups (done):**
  - `sessionStore.test.ts` uses `ARM` from `test/msw/handlers.ts`; `fakeJwt.ts` takes `aud` from `API_RESOURCES[api].resource`.
  - Layering is enforced by `no-restricted-imports` per folder (`LAYERS` in `eslint.config.js`), for both `@/` and relative imports. Tests are exempt.
  - CSP: no milestone owned it. Done in M4 (below).
- **Code quality review follow-ups (done), most severe first.** Fixed before M2 builds on the client:
  - ~~Validation failures after `send()` are logged as `ok`.~~ Done: `send()` validates against a Zod schema before finishing the log entry, and `getJson` / `getJsonOrNull` / `getAllPages` accept a `schema` for services. A `$batch` log line shows how many sub-responses failed.
  - ~~Requests have no timeout.~~ Done: each attempt combines the caller's signal with `AbortSignal.timeout(requestTimeoutMs)` (default 30 s, counted from leaving the queue, covering the body read) and fails as kind `timeout`. Queued limiter tasks drop out when their signal aborts.
  - ~~`send()` (85 lines) does everything.~~ Done: split into `fetchWithRetry()` (send + retries), `readResponse()` (no I/O: received response → `Outcome`) and `settleLog()` (log entry matches the caller's result). One catch now covers fetch, retry wait and body read.
  - ~~`batchChunk` cleanup.~~ Done: pure `partitionBatchResponses()`, `sendBatch()`, the shared retry-budget rule commented, clearer names. Unknown, duplicate or missing sub-response ids fail the POST as `invalid-response` via the schema (`batchAnswerMismatch()`), so the log line is an error.
  - ~~Renames.~~ Done: `HttpErrorKind 'http'` → `'unexpected-status'`, `TokenClaims.aud` → `displayAudience`, `upn` → `signInName`, `TokenWarning` → `TokenIssue` (`isBlockingWarning` → `isBlockingIssue`). An undecodable token fails as `invalid-token` instead of `audience-mismatch`.

**M2 — `services/` (raw layer, Zod-validated)**
- Every ID put into a path (`sub`, `svc`, `apiId`, `opId`, `backendId` from policy XML, Graph `id`) goes through `encodePathSegment()`. Test: a policy with `backend-id="../../x"` gives a per-resource `invalid-request` error and sends nothing.
- `services/arm` (**done**): subscriptions (`/subscriptions`, api-version `2022-12-01`), services (including `identity.userAssignedIdentities` with `clientId`/`principalId`), APIs (list for the picker, including `serviceUrl`). For the selected API only: operations, policies at global / API / operation scope (`format=rawxml`, where 404 means "no policy"), and each referenced backend via `backends/{backendId}` (URL only, no `GET {resourceId}`). Products, fragments and named values are out of scope (§1).
- `services/graph` (**done**):
  - service principal lookups: by appId, by id, by `servicePrincipalNames` filter (used for both the inbound `audience` and the outbound `resource`)
  - `appRoles`, `appRoleAssignedTo` (inbound) and the user-assigned identity's `appRoleAssignments` (outbound)
  - groups and their *direct* members, with group-type members filtered out
  - a `$batch` helper that chunks requests into groups of 20 (`batchGet`, `getServicePrincipalsByIds`), with a ResourceResult per lookup
  - Service principal owners are out of scope and not fetched.
- Each call gets a TanStack Query hook with stable keys (`['arm', sub, svc, 'apis']`, `['graph','sp',appId]`, …). **Done.**
- Errors are kept per resource; nothing fails globally.

**M3 — `domain/` (pure TS; this is the bulk of the tests)**
- `model.ts`: the types listed in CLAUDE.md, as discriminated unions.
- `policy-parser/` (**done**):
  - fast-xml-parser configured to *preserve order* (needed for `<base/>` placement and "last `set-backend-service` wins")
  - effective-policy composition per section: global → API → operation. A missing `<base/>` drops the parent's section, and that gets recorded.
  - extractors (§1 pattern): `validate-jwt`, `set-backend-service backend-id`, `authentication-managed-identity`
  - classifying `inbound` / `backend` elements: handled, ignorable (response-only), or `UnresolvedRule` (anything else, including `@(...)` in an access/routing attribute)
- `mapper/` (**done**): joins rules with Entra data into `AccessEdge[]`. Known limitation: each path (direct, or one group) is checked on its own, so a user who meets `match="all"` only by combining a direct role with a group role is not found. With `match="any"` (the target pattern) this never matters.
  - inbound: audience → API service principal → roles → `appRoleAssignedTo` → principals → direct group members
  - outbound: `client-id` → user-assigned identity → `appRoleAssignments` on the `resource` service principal
  - SP/MI members of groups are marked `effective: false` with a reason
  - a required role that doesn't exist in the API's `appRoles` is a finding
  - findings: no auth, parent inbound ignored, no outbound auth, HTTP backend, APIM identity holding no role on the backend
- `useAccessModel()` (**done**): orchestrates the queries and builds the model incrementally, so views render partial data with progress (`model.pending`). **M3 is complete.**

## 3. Key design decisions

- **Request log is a side effect of `lib/http`**. Views and services never log manually, so new views get logging for free.
- **Ordered XML parsing.** fast-xml-parser's `preserveOrder: true` is required for correctness around `<base/>`. I'll wrap it in a small typed tree helper so extractors don't handle raw arrays.
- **Read-only guard at runtime and in tests.** A test asserts the wrapper throws on any non-GET (except the validated `$batch`).
- **MSW serves both tests and `pnpm dev`** (a "demo mode" with fictional fixture data), so the app can be developed and demoed without a token.
